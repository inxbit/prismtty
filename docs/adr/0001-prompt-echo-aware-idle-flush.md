# Prompt-echo-aware idle flush of the buffered token

**Status:** accepted

The interactive `StreamingHighlighter` speculatively holds the trailing token of each output chunk in `pending` so a token split across reads still highlights as one unit. The original idle flush (the `nsupdate` raw-mode fix) surfaced that buffered token only when it byte-matched recently forwarded keyboard input (`consume_echo_suffix`). Device-side word completion breaks that match: when a user presses Tab at a Cisco Nexus prompt, the device redraws `host# sh log` (often completing the typed `sh lo` into `sh log`) ending in a bare token with no delimiter, then goes idle, and the trailing token is neither echoed input nor a byte-suffix of what was typed, so it stayed invisible until the next keystroke. We decided to add a **second, independent flush trigger** gated on three conditions together: (1) **provenance** - the buffered token was split off a prompt-echo redraw remainder (a `pending_from_prompt_echo_remainder` flag; program output buffered by the normal streaming split never qualifies); (2) **shape** - the highlighter's current visible line is a recognized prompt-echo line (`contains_prompt_echo_in_visible_line`); and (3) **strict idle** - the input source polls clean-idle (`poll == 0`; a poll error is *not* treated as idle, unlike the lenient check the byte-match path keeps). On all three, flush the buffered token regardless of any recent-input match. We chose provenance gating over making prompt-echo remainders non-buffering because it is purely additive; no existing emit/highlight bytes change.

## Consequences

- **Screen-safety is unchanged.** The flush still only ever emits the child's own output bytes (`pending`), never `recent_input`. A non-echoed secret (sudo/ssh password) produces no buffered token, and a `Password:`-style line is not a prompt-echo line (it has no `#`/`>`/`$`/`%` marker followed by command text), so the trigger cannot fire on it. Program output buffered by the normal streaming split has provenance `false`, so it is never flushed early either. The security boundary stays "only emit child output," not "only flush on a recent-input match."
- **Vendor-agnostic and durable.** Any device that redraws `prompt# command` and idles (Cisco, Arista, Juniper, etc.) now surfaces the tail, so this class of "disappearing command tail after Tab/`?` completion" does not recur per-vendor.
- **Accepted limitation.** If a device split a single redraw across two writes with a strict clean-idle gap (`poll == 0`) between them, flushing on the gap could split one highlight span into two. This is cosmetic (never a security or text-loss issue), is gated by the strict clean-idle poll, and is strictly better than the prior behavior (invisible text). Required regression guards bound the trigger's breadth: a program-output-that-looks-like-a-prompt span test, multi-write redraws, `--More--` paging, password-after-prompt output, and local-shell completion.
- The recent-input byte-match path is retained with a trailing completion-trigger trim as a cheap fallback for non-prompt redraws that end in a typed token.
