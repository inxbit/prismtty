# Prompt-echo-aware idle flush of the buffered token

**Status:** accepted

The interactive `StreamingHighlighter` speculatively holds the trailing token of each output chunk in `pending` so a token split across reads still highlights as one unit. The original idle flush (the `nsupdate` raw-mode fix) surfaced that buffered token only when it byte-matched recently forwarded keyboard input (`consume_echo_suffix`). Device-side word completion breaks that match: when a user presses Tab at a Cisco Nexus prompt, the device redraws `host# sh log` (often completing the typed `sh lo` into `sh log`) ending in a bare token with no delimiter, then goes idle, and the trailing token is neither echoed input nor a byte-suffix of what was typed, so it stayed invisible until the next keystroke. We decided to add a **second, independent flush trigger** gated on three conditions together: (1) **provenance** - the buffered token was split off a prompt-echo redraw remainder (a `pending_from_prompt_echo_remainder` flag; program output buffered by the normal streaming split never qualifies); (2) **shape** - the highlighter's current visible line is a recognized prompt-echo line (`contains_prompt_echo_in_visible_line`); and (3) **strict idle** - the input source polls clean-idle (`poll == 0`; a poll error is *not* treated as idle, unlike the lenient check the byte-match path keeps). On all three, flush the buffered token regardless of any recent-input match. We chose provenance gating over making prompt-echo remainders non-buffering because it is purely additive; no existing emit/highlight bytes change.

## Consequences

- **Screen-safety is unchanged.** The flush still only ever emits the child's own output bytes (`pending`), never `recent_input`. A non-echoed secret (sudo/ssh password) produces no buffered token, and a `Password:`-style line is not a prompt-echo line (it has no `#`/`>`/`$`/`%` marker followed by command text), so the trigger cannot fire on it. Program output buffered by the normal streaming split has provenance `false`, so it is never flushed early either. The security boundary stays "only emit child output," not "only flush on a recent-input match."
- **Vendor-agnostic and durable.** Any device that redraws `prompt# command` and idles (Cisco, Arista, Juniper, etc.) now surfaces the tail, so this class of "disappearing command tail after Tab/`?` completion" does not recur per-vendor.
- **Accepted limitation.** If a device split a single redraw across two writes with a strict clean-idle gap (`poll == 0`) between them, flushing on the gap could split one highlight span into two. This is cosmetic (never a security or text-loss issue), is gated by the strict clean-idle poll, and is strictly better than the prior behavior (invisible text). Required regression guards bound the trigger's breadth: a program-output-that-looks-like-a-prompt span test, multi-write redraws, `--More--` paging, password-after-prompt output, and local-shell completion.
- The recent-input byte-match path is retained with a trailing completion-trigger trim as a cheap fallback for non-prompt redraws that end in a typed token.

## Amendment: line-edit redraws (2026-08-20)

A live `ptty` session over `ssh` surfaced a third redraw shape the two triggers above cannot cover. Recalling a command from shell history with an arrow key makes the remote line editor **backspace over the current input line and rewrite it**; when the recalled command ends mid-token (`... username=operator`, no delimiter after the `=`), that token is buffered and stranded. Trigger 1 cannot fire because the keystroke is `ESC [ A`, nothing like the recalled text. Trigger 2 cannot fire because the redraw carries no prompt: the shell moved the cursor to the previous line with cursor-positioning controls, so `visible_line_tail` holds only the rewritten command and `contains_prompt_echo_in_visible_line` is false. The tail stayed invisible until the next keypress.

We add a **third trigger** with the same two-part structure as the second — provenance plus shape, the same strict clean-idle gate, and the same hands-off treatment of `recent_input`. The prompt-echo logic is untouched.

- **Provenance** (`pending_from_interactive_split`): the buffered tail came from the ordinary interactive split rather than a prompt-echo remainder. Its only job is keeping triggers 2 and 3 disjoint.
- **Shape** (`visible_line_was_rewritten_in_place`): the accumulated visible line carries a backspace, so something moved back over text already on the line and wrote over it.

The shape is deliberately read from **the line, not the chunk**. A first attempt tested the stranding chunk itself for a leading backspace; adversarial review then produced live-PTY traces showing that a redraw split across two reads (`printf '\b\b\bvault login'; sleep 0.4; printf ' ... username=operator'`) strands its tail on a read that carries no backspace at all, reproducing the original symptom in full — and ssh, the reported transport, splits a remote line editor's writes routinely. The same hole opened when an earlier echo token was still buffered, since the highlighter prepends `pending` to the incoming chunk. Reading the accumulated line closes both for reads the line tracker observes. One window remains, inherited from the prompt-echo repaint machinery: a chunk that qualifies for prompt-echo preservation is not observed at all, so backspaces inside it are lost to the signal (the pre-fix behaviour for that segmentation), and a `\r`/`\n` inside it does not reset the line, so a stale signal can arm one early flush on a later line (the accepted cosmetic class).

### Consequences

- **The signal is per-line, not per-chunk.** It survives every read on the rewritten line and is gone at the next `\r`/`\n` the line tracker observes. `tests/interactive_paste.rs::split_history_recall_redraw_tail_is_visible_without_extra_input` pins the split delivery on a real PTY; `line_edit_redraw_signal_is_scoped_to_the_rewritten_line` pins the survival half and the `\r` reset; `bare_lf_clears_the_rewritten_line_signal` pins the `\n` reset.
- **Bare-CR rewrites stay excluded.** That is the shape every progress bar emits on each update, and covering it would arm the flush during continuous output. Widen only against a trace that shows a real failure. Cursor-movement rewrites (CSI moves and erases, zle's redraw beyond short distances) are likewise excluded: a single-read CSI redraw passes through whole, and only a split-delivered CSI rewrite on a promptless line strands.
- **Accepted limitation, same class as trigger 2, slightly broader than the first draft.** Any line rewritten in place with a backspace — an in-place byte counter, an overstrike — now flushes a stranded tail early once the source goes clean-idle. Worst case one highlight span is drawn as two. Cosmetic, never text loss, and the flushed bytes are ones the child was going to draw anyway.
- **Bounded under-fire.** The visible line tail is capped at 512 bytes, so a rewritten line longer than that can age its backspace out and stop qualifying. That costs the flush — the pre-fix behaviour — never correctness.
- **Screen-safety is unchanged**, for the same reason as trigger 2: only the child's own buffered output bytes are ever emitted, never `recent_input`, so a non-echoed secret still produces no token to draw.
- **Alternate screen is excluded.** Alt-screen chunks are never observed by the line tracker, and entering or leaving the alternate screen clears the tracked line, so an app's own backspaces (xterm's `cub1` is `^H`) cannot arm the trigger afterwards. Bytes coalesced into the same read as the screen switch are unobserved, which at most costs the flush, never correctness.
- Guards: two live PTY regression tests (single-read and split delivery, both failing without the change with exactly the reported screen state), the read-loop gate and `highlight_stream` wiring tests, a negative test pinning the strict-idle conjunct (deleting it left the whole suite green before), and shape negatives for bulk output, `\r` rewrites and line-crossing chunks, a pending-token-prefix positive, a provenance negative keeping triggers 2 and 3 disjoint, alternate-screen round-trip negatives, and white-box guards on the alternate-screen conjunct and the bare-`\n` reset.
